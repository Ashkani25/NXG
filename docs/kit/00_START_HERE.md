# NEXORA Agent Kit — از اینجا شروع کن

این بسته برای یک ایجنت هوش مصنوعی کدنویس (مثل Claude Code) نوشته شده است تا پروژه NEXORA را از صفر تا انتشار بسازد.

## ساختار بسته
- `00_START_HERE.md` : همین فایل، قوانین کار.
- `01_VISION_AND_CONTEXT.md` : ایده کامل، پیش‌زمینه و ذهنیت صاحب پروژه. قبل از هر کاری کامل بخوان.
- `02_ROADMAP_30_PARAMETERS.md` : ۳۰ پارامتر ثابت نقشه راه (تصمیم‌های فنی و محصولی).
- `03_ASSET_GUIDE.md` + `assets/` + `assets_manifest.json` : دارایی‌های گرافیکی برش‌خورده، نام‌گذاری‌شده و آماده‌ی اپ.
- `04_FINGER_SOCCER_SPEC.md` + `samples/finger_soccer/` : طراحی و نمونه‌ی کامل بازی Finger Soccer (Flutter/Dart/Flame + Supabase).
- `05_TOOLING_ACCESS.md` : دسترسی ترمینال به Supabase، GitHub و LiveKit و قواعد ایمنی.
- `06_PROMPTS.md` : پرامپت‌های آماده (شروع، اجرای مرحله، ادامه، ممیزی، تولید دارایی).
- `steps/STEP_01 ... STEP_30` : ۳۰ دستورالعمل متصل به هم. هر مرحله روی خروجی مرحله قبل ساخته می‌شود.

## پروتکل اجرا (اجباری)
1. ابتدا فایل‌های ۰۱ تا ۰۶ را کامل بخوان و خلاصه‌ی ۱۰ خطی از درکت بنویس (در `docs/UNDERSTANDING.md`).
2. مراحل را **به ترتیب** اجرا کن. از مرحله‌ای رد نشو و مرحله بعد را شروع نکن مگر معیار پذیرش (DoD) مرحله فعلی کامل برقرار باشد.
3. بعد از هر مرحله این‌ها را به‌روز کن:
   - `docs/PROGRESS.md` : مرحله انجام‌شده، تاریخ، خروجی‌ها، مشکلات باز.
   - `docs/DECISIONS.md` : هر تصمیم فنی مهم با دلیل (ADR کوتاه).
   - `docs/HANDOFF.md` : آنچه مرحله بعد باید بداند (مسیر فایل‌ها، نام کلاس‌ها، قراردادها).
4. هر قابلیت باید **واقعاً کار کند**. هیچ دکمه، آمار، پیام یا پاسخ ORACLE نباید ساختگی (fake/mock) در نسخه نهایی باشد. اگر چیزی هنوز ساخته نشده، در رابط کاربری به‌صراحت «به‌زودی» نشان بده، نه اینکه وانمود به کار کردن کند.
5. ساخت APK/AAB فقط از طریق GitHub Actions انجام می‌شود، نه روی گوشی. فرض کن صاحب پروژه تنها از گوشی کار می‌کند؛ پس خروجی‌ها باید با push به GitHub و دانلود artifact قابل تست باشند.
6. وقتی چیزی مبهم است، **حدس نزن**: سؤال کوتاه بپرس یا بهترین گزینه را انتخاب کن و در `DECISIONS.md` ثبت کن.
7. اگر وابستگی (package) یا سرویس پولی لازم شد، قبل از استفاده گزینه رایگان/کم‌هزینه را بررسی کن و تصمیم را ثبت کن. ترجیح صاحب پروژه: کم‌هزینه یا رایگان.
8. هر مرحله باید تست مرتبط داشته باشد (unit / widget / integration به‌اندازه مناسب) و `flutter analyze` بدون خطا باشد.
9. کد نباید مرحله‌های قبل را بشکند. قبل از merge، تست‌های مراحل قبل را اجرا کن.
10. زبان رابط: فارسی (RTL) و انگلیسی. کد و نام‌ها انگلیسی، توضیحات می‌تواند فارسی باشد.

## قالب هر مرحله
ورودی → هدف → دستورالعمل‌ها → تأکید گرافیک و معماری → خروجی‌ها → معیار پذیرش → تحویل به مرحله بعد.

## اصل طلایی
زیبایی نباید استفاده را سخت یا برنامه را کند کند. هر جلوه بصری باید راه فرار داشته باشد: رد کردن، کیفیت پایین‌تر، کاهش حرکت.

## ابزارها
ایجنت به **ترمینال، GitHub، Supabase و LiveKit دسترسی کامل** دارد و باید همه چیز را خودش تا آخر انجام دهد (ساخت، استقرار، تست، انتشار). قواعد در `05_TOOLING_ACCESS.md`.
